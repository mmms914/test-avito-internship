# Meeting Room Booking Service

Сервис для бронирования переговорных комнат с JWT-авторизацией и интеграцией с внешним сервисом конференц-связи. Был написан в качестве [тестового задания](/TASK.md) при отборе в Avito Tech.

## Обзор

Проект демонстрирует реализацию REST API для управления бронированием переговорок.  
Основное внимание уделено:
- Чистой архитектуре с разделением на слои (domain, service, repository, handlers)
- Надёжной работе под нагрузкой (100 RPS, 99.9% успешных ответов)
- Тестированию (юнит, интеграционное, E2E, нагрузочное)

### Архитектурные решения
Проект структурирован по слоям:

```
internal/
├── domain/          # Сущности 
├── service/         # Сценарии использования
├── repository/      # Интерфейсы доступа к данным и их реализации
├── api/
│   ├── handlers/    # HTTP‑обработчики
│   └── middleware/  # Аутентификация, логирование
├── infra/           # Внешние зависимости (БД, мок‑сервис сервиса проведения конференций)
└── config/          # Конфигурация приложения
```

### Генерация слотов «по требованию»
Слоты для бронирования создаются в момент первого запроса списка доступных слотов на конкретную дату.
Преимущества подхода:
- Не тратим память на дни, к которым нет интереса
- Первый запрос чуть медленнее, последующие — мгновенные
- Для рабочей недели (наиболее востребованный диапазон) накладные расходы минимальны

### Обработка внешнего сервиса конференц‑связи
При создании брони с флагом createConferenceLink = true сервис запрашивает ссылку у мокового Conference Service до сохранения брони в БД.
В случае сбоя сохранения выполняется однократная компенсирующая операция — попытка отменить полученную ссылку. При неудаче компенсации ошибка логируется, а клиент получает сообщение об ошибке создания брони.
Аналогичный подход используется при отмене бронирования, но может быть улучшен, например, применением паттерна Outbox.

### Тестирование
#### Юнит‑тесты
Полностью покрывают сервисный слой и доменные объекты, а также валидацию в хендлерах.

Запуск:
```bash
make test-unit
````

#### Интеграционные тесты
Покрывают слой репозитория с поднятием тестовой БД.
Тесты находятся в test/integration

Запуск: 
```bash
make test-integration
````

### E2E-тесты
- **Сценарий 1**: создание комнаты → создание расписания → бронирование слота пользователем
- **Сценарий 2**: отмена существующей брони

Тесты находятся в test/e2e/booking_test.go

Запуск:
```bash
make test-e2e
````

#### Покрытие кода
Для оценки совокупного покрытия (юнит + интеграционные) используется команда:

```bash
make coverage-all
```
Текущее значение — 43.6%.

_Примечание: моки и код, связанный с конфигурацией, не включаются в осмысленное покрытие._

#### Нагрузочное тестирование
Основной целевой эндпоинт — **GET /rooms/{roomId}/slots/list** — протестирован на 100 RPS.
Каждый воркер запрашивает слоты на случайную дату в пределах 5 лет, что часто приводит к генерации новых слотов «на лету».

Пример результатов одного из прогонов:

![Результаты нагрузочного тестирования](/images/img_1.png)

Среднее время ответа остаётся в пределах 200 мс, что удовлетворяет заданному SLI.

Запуск:
```bash
make test-load
```
